01 / Executive brief

The problem is not generating code. It is proving the agent did the right work.

ModernizeBench is an evaluation and experimentation platform for agentic software engineering. Its first benchmark asks multi-agent systems to recover a feature from a legacy PHP application and rebuild it in Spring Boot and React while preserving business behavior.

The core proposition:

Package real work as reproducible Task Packs; run any compatible agent workflow; capture what happened; grade both the result and the path; repeat the task enough times to measure reliability; then turn failures into new evaluation cases.

What it is

  • A benchmark harness for long-horizon software work
  • An observability and trace-normalization layer
  • A grader framework for business and engineering invariants
  • An experiment system for prompts, models, tools, memory, and workflow design
  • A public research and learning project

What it is not

  • Not another generic chatbot builder
  • Not a promise that migration can be fully autonomous
  • Not a single opaque LLM quality score
  • Not tied permanently to GitHub Copilot or one model vendor
  • Not a replacement for architecture, security, or business accountability

02 / Business view

Why an organisation would care.

Agentic development can reduce exploration and implementation effort, but it introduces a new assurance problem. Traditional tests can confirm that code compiles; they rarely confirm that the agent found every scattered rule, interpreted the data model correctly, reused the right enterprise capability, or stayed within policy.

ENGINEERING

Change with confidence

Catch regressions in agent prompts, tools, models, memory, and workflow topology before they reach delivery teams.

BUSINESS

Preserve domain behavior

Trace every recovered requirement to evidence and verify customer-visible behavior and hidden side effects.

RISK & SECURITY

Control autonomy

Measure permissions, approvals, scope, secret exposure, unsafe commands, and policy compliance.

PLATFORM

Compare investments

Quantify quality, reliability, cost, latency, and failure modes across agent frameworks and model choices.

04 / Operating model

The end-to-end modernization and evaluation loop.

01 DISCOVERMap routes, templates, code, SQL, schema, roles, and integrations.
02 RECOVERProduce evidence-backed requirements and uncertainty.
03 DESIGNCreate target boundaries, contracts, data and reuse decisions.
04 IMPLEMENTBuild Spring, React, migrations, tests, and observability.
05 VERIFYRun parity, state, contract, security, and policy graders.
06 REPEATExecute multiple trials and compare configurations.
07 LEARNCluster failures and add tasks, graders, or workflow fixes.

The agent workflow is the system under test. ModernizeBench does not assume one correct orchestration. It compares workflows through common Task Packs, trace contracts, and graders.

06 / Task Packs

The unit of reproducible work.

A Task Pack defines everything needed to start, run, reset, and grade one realistic task. It is both a benchmark instance and an executable product requirement.

task-pack/
├── task.yaml          # identity, version, capability, budgets
├── instruction.md     # agent-visible objective
├── legacy/            # starting repository
├── target-skeleton/   # allowed destination structure
├── environment/       # containers, services, network policy
├── fixtures/          # database and external-system state
├── policies/          # permissions, approvals, prohibited actions
├── references/        # reviewer-only gold evidence
├── graders/           # hidden outcome and process assertions
└── reset/             # deterministic reset and health checks

Quality requirements

  • A human can solve the task from the stated information.
  • Hidden graders enforce stated behavior rather than surprise requirements.
  • The environment can be reset and fingerprinted.
  • Agent-visible and evaluator-only data are separated.
  • Every change creates a new version and runs gold-solution validation.

07 / Runner portability

Evaluate the workflow, not the vendor.

The first adapter imports the existing Copilot agent workflow, including agent definitions, handoffs, hooks, session artifacts, and tool calls. A small internal runner contract keeps the platform open to additional runtimes.

Runner input

  • Task Pack and workspace
  • Workflow definition and version
  • Model and inference configuration
  • Tool endpoints and permissions
  • Budget and stop conditions
  • Trace exporter and artifact sink

Runner output

  • Terminal status and stop reason
  • Produced artifacts and repository diff
  • Canonical and raw traces
  • Usage, cost, and timing
  • Human interventions
  • Infrastructure diagnostics

Framework-specific capabilities may remain visible as metadata, but the evaluation contract stays stable.

08 / Portable intelligence

Schema Index and Reuse Scout become evaluated platform services.

Schema and repository intelligence

Search tables, columns, relationships, routes, symbols, SQL usage, read and write paths, business entities, and evidence provenance.

Evaluation: retrieval recall, precision, argument correctness, evidence use, stale-index behavior, and permissions.

Reuse Scout

Find similar implementations, compare candidates, inspect contracts and examples, check compatibility, and explain selection or rejection.

Evaluation: candidate ranking, compatibility reasoning, actual downstream reuse, duplication avoided, and false-positive cost.

Both services sit behind internal interfaces and expose MCP adapters. This protects the domain model from protocol evolution and permits direct SDK use in controlled environments.

09 / Evaluation methodology

Five dimensions, multiple graders, no opaque magic score.

DimensionCore questionsPrimary evidence
OutcomeDid the new system preserve intended behavior?Tests, state assertions, contracts, UI flows, static analysis
Evidence and reasoningWere requirements and decisions grounded?Evidence graph, citations, rubric graders, uncertainty register
TrajectoryWere the right tools, approvals, and verification steps used?Canonical trace, process invariants, arguments, milestones
ReliabilityDoes it work repeatedly across tasks and runs?Repeated trials, confidence intervals, failure slices
Safety and economicsDid it remain in scope at acceptable cost and speed?Policy events, sandbox logs, tokens, reviewer time, latency

Grader hierarchy

  1. Deterministic graders: executable truth and release gates.
  2. Model graders: semantic qualities with narrow rubrics and calibration.
  3. Human review: disputed, high-risk, or novel cases.
  4. Composite decision: explicit thresholds and veto conditions, while raw scores remain visible.

10 / Evidence and trace model

A portable causal record of the run.

The canonical trace uses trace, span, event, and attribute concepts and maps framework-native data into a stable internal schema. It records model turns, agents, handoffs, tools, approvals, memory reads, workspace mutations, tests, and graders.

Identity

Task, trial, workflow, model, runner, environment, prompt, tool, grader, and commit versions.

Causality

Parent-child spans, linked parallel work, handoff origin, retry lineage, and approval dependency.

Evidence

Artifact hashes, source pointers, tool arguments and outputs, state snapshots, screenshots, and diffs.

Raw provider events are retained for forensic analysis. Sensitive-content capture, redaction, retention, and access are configurable and auditable.

11 / Reliability and experimentation

One successful demo is an anecdote.

Every meaningful comparison uses repeated trials and paired tasks. ModernizeBench reports per-task outcomes, distributions, confidence intervals, failure clusters, cost, latency, and repeated-success probability.

Example experiment:

Compare no memory, summary memory, and structured evidence memory on the same ten tasks with five trials each. Measure business-rule fidelity, repeated repository exploration, stale assumptions, total tokens, wall time, and three-run consecutive success.

Experiments require immutable configuration snapshots. Model, workflow, tools, prompts, memory policy, environment, task, and graders are separately versioned so causal claims remain possible.

12 / Security and governance

Autonomy is risk-tiered, not binary.

Execution controls

  • Isolated workspaces and trusted grader boundary
  • Read-only by default; scoped writes
  • Network allowlists and egress logging
  • Short-lived credentials outside model context
  • CPU, memory, time, and storage limits

Governance controls

  • Versioned policies and approvals
  • Risk-tiered autonomy profiles
  • Evidence packets for reviewers
  • Audit logs, exceptions, and risk acceptance
  • Incident-to-eval feedback loop

Security graders test prompt injection, tool poisoning, secret access, out-of-scope changes, destructive commands, approval bypass, and data exfiltration.

14 / Differentiation

Why this is more defensible than another coding agent.

  • Behavioral reconstruction: the benchmark starts before implementation, with evidence-backed business archaeology.
  • Cross-stack scope: legacy code, UI, database, target backend, frontend, contracts, and operational effects.
  • Outcome plus process: it grades what was built and how the agent got there.
  • Framework-neutral comparison: workflow and model can change without changing the task claim.
  • Enterprise controls: approvals, permissions, evidence, traceability, and risk-tiered autonomy are first-class.
  • Research flywheel: every failure can become a new task, grader, policy, or experiment.

16 / FAQ and glossary

Questions the pitch should answer.

Why not just use unit and integration tests?

Use them—they are core deterministic graders. ModernizeBench adds task definitions, repeated trials, trajectory evidence, model and tool versioning, failure analysis, and cross-workflow comparison.

Does a higher benchmark score mean production-ready?

No. It supports a bounded claim for a defined task population and environment. Production readiness also requires organisational controls, security review, deployment testing, and monitored operation.

Why modernization first?

It is long-horizon, cross-stack, evidence-heavy, and business-sensitive. It exposes weaknesses that short coding tasks hide while building on an existing real workflow.

Will it replace developers or architects?

The design assumes human accountability. It aims to automate exploration and implementation while making evidence and decisions easier to review.

What is a grader?

A function or review process that scores an aspect of a trial. Graders may execute code, inspect state, apply a calibrated rubric, or request human judgment.

What is trajectory evaluation?

Evaluation of the sequence of actions—tools, arguments, evidence, handoffs, retries, approvals, and verification—rather than only the final output.
